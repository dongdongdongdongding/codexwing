이슈 `swing-main-l64n`, 구현 `54fc4d8`, 후속 `6dfcec2`, `4baaed9`, `afbb46e`.

기존 `com.codex.swing.dailyops`는 300초 간격 작업이지만, 폴러 자체에서
스캔과 전체 배치를 동기 실행했다. 실제 10:01 KST에도 05:07에 시작한
PID 54858 → 전체 배치 75970이 실행 중이었고 09:35 국내 세션은 시작되지
않았다. 최신 경계 catch-up은 이미 있었으나 실행 중 다음 폴링이 불가능했다.

`--run-due`의 기본 동작을 불변 세션 요청 기록 후 즉시 반환으로 바꿨다.
`--synchronous`는 명시적인 수동 진단 경로이며, `--dry-run`은 기존 모의
실행을 유지한다. 새 짧은 폴러와 국내 스캔·미국 스캔·전체 배치 작업자가
각각 launchd에서 실행된다. 등록 도구는
`python3 scripts/install_primary_session_workers.py --install`이다.

| 역할 | launchd label | 간격 |
|---|---|---:|
| 요청 접수 | com.codex.swing.primary-dispatch | 60초 |
| 국내 스캔 | com.codex.swing.primary-worker-kr-scan | 60초 |
| 미국 스캔 | com.codex.swing.primary-worker-us-scan | 60초 |
| 전체 배치 | com.codex.swing.primary-worker-daily-ops | 60초 |

각 작업자는 자기 역할의 파일 잠금을 작업 종료까지 유지한다. 기존 수동/
구버전 프로세스도 실제 `ps`에서 확인해 같은 명령의 중복 실행을 막는다.
전체 배치는 시작 전에 접수된 동일 설정 요청들을 한 번에 처리한다.
실행 도중 추가된 요청은 그 배치의 완료로 처리하지 않는다. 미실행 스캔은
최신 경계만 실행하고 이전 요청은 superseded, 시장 현지 날짜가 지난 요청은
expired 사유로 기록한다. 실제 실행 시각과 요청 시각을 보존하며 과거 시각의
체결/스캔 증거를 만들어내지 않는다.

요청/명령별 결과는 `runtime_state/long_term/ops/session_dispatch/`에 있다.
완료 전에는 상태를 running으로 표시하고, 전체 배치 실패는 failed,
스캔 실패/대체는 degraded로 집계한다. 중단된 작업의 결과가 불명확하면
interrupted 실패를 기록하고 자동 중복 실행하지 않는다. 변경 없는 과거
결과를 폴링 시각으로 재기록하지 않는다. 기존 프로세스가 낡은 전체 상태를
덮더라도 불변 요청/결과로 다음 폴링에서 복원한다. 복구 작업자의 Discord와
외부 webhook 알림은 dry-run이며 실제 계산/DB 저장은 실행한다.

운영에서 10:11:31 KST에 국내 작업자 PID 63570 → 스캔 63588,
미국 작업자 63572 → 스캔 63587이 시작됐다. 10:12:51에도 기존 전체 배치
75970은 실행 중이었고 새 전체 배치 결과 파일은 생성되지 않았다. 즉 기존
