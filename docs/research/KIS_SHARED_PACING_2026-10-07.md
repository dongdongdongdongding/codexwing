# KIS 프로세스 간 호출 간격

2026-10-07, `swing-main-mm5r`, 최종 코드 `85b64f4`.

기존 `_live_request_throttle`은 스레드 잠금과 프로세스 안의 마지막 호출
시각만 사용했다. 여러 시장 작업자가 병행 실행되면 각각 설정 간격을
지켜도 전체 호출 간격은 공유되지 않았다. 과거 44개 요청 오류의 원인이
이 문제였다고 주장하지 않는다. 그 오류 기록에는 공급사 코드가 없었다.

현재는 `~/.cache/codex_swing/kis_live_rate.json`의 같은 파일을 잠그고,
호스트 공통 `CLOCK_MONOTONIC`으로 호출 간격을 계산한다. 파일을 교체하지
않아 모든 프로세스가 같은 inode를 잠근다. 파일에는 시계 종류·시각·간격만
저장하며 API 키/토큰/계좌 정보는 없다. 기본 간격 0.12초는 유지한다.
앞 요청과 다음 요청의 설정이 다르면 큰 간격을 적용한다. 빈/손상/구형
시계 기록은 한 간격을 기다린 뒤 복구하고, 기록을 열 수 없으면 네트워크
호출을 진행하지 않는다. 0 이하로 명시한 기존 비활성 설정은 유지한다.

운영 `.env.local`과 실행 환경에는 간격/상태 경로 override가 없었으므로
기본 공통 경로와 0.12초를 사용한다. 테스트 격리를 위한
`KIS_LIVE_RATE_STATE_PATH`는 지원하지만, 운영 작업자마다 다른 경로를
주면 예산도 나뉘므로 그런 설정을 사용하지 않는다. 범위는 같은 호스트의
새 코드를 읽은 프로세스들이며 다른 호스트/외부 프로그램의 호출은 제어하지 않는다.

## 처음 검증에서 놓친 시계 차이와 수정

최초 구현 `7670353`은 공유 파일에 `time.monotonic()`을 기록했다.
거의 동시에 시작한 프로세스와 각 프로세스의 로컬 시각을 비교한 검사가
잘못 통과했다. 운영 Python 3.9.6/macOS에서 실제 측정해 보니
`monotonic()`은 약 0.0086, `clock_gettime(CLOCK_MONOTONIC)`은 약
2,800,527초였다. 프로세스별 기준점 차이를 놓친 것이다.
[Python 공식 문서](https://docs.python.org/3/library/time.html#time.monotonic)도
macOS의 프로세스 공통 monotonic 시계 변경 시점을 Python 3.10으로 명시한다.

시작을 0.4초 지연한 프로세스를 포함하고 공통 시스템 시계로 관측하도록
검사를 강화하자 구형 구현에서 최소 간격 **0.000161초**로 실패를 재현했다.
`85b64f4`에서 시계와 기록 형식 식별자를 수정했다. 최초 운영 측정 파일은
삭제하지 않고 `INVALID_FOR_CROSS_PROCESS_CLOCKS`로 정정했다.

최종 관련 검사 63개 통과: 시작 시점이 다른 4개 프로세스의 네트워크 진입
12회, 종료된 잠금 소유자 복구, 손상/구형/재부팅 시계 기록, inode 유지,
간격 변경, 저장 실패 시 네트워크 차단, 비유한 설정 거부 및 기존 API/수집/
세션 실행 검사를 포함한다. 최초 테스트용 KISConfig의 필수 인자 누락도
고쳤고, 시작하지 못한 자식 프로세스를 즉시 검사하도록 보강했다.

## 운영 검증

최종 코드에서 **1초 차이로 시작한 두 프로세스**가 고정 005930 일봉을
각 3회 조회했다. 6회 모두 `rt_cd=0`, 각 5행 반환, stderr 0.
공통 시계로 관측한 네트워크 진입 최소 간격은 **0.126475초**였다.
이 읽기 검증은 시장 데이터 캐시를 변경하지 않았다.

증거: 운영 `runtime_state/audit/kis_shared_pacing_20261007/`의
원래 검사와 정정 표시, `attempt2_host_clock/live_probe_result.json`,
`workers_after_deploy.json`.

배포 전 시작한 작업을 중단하거나 재실행하지 않았다. 이들은 이미 읽은
구형 코드를 계속 사용하므로 모든 실행 중 작업에 소급 적용됐다고 말할 수
없다. 10:35 KST 점검에서 국내 스캔은 10:33:14 종료 코드 0으로 끝났고,
미국 스캔 PID 63587 및 기존 전체 배치 PID 75970은 계속 실행 중이었다.
장시간 작업의 종료 확인은 `swing-main-l64n`에 남긴다. 본 변경은 호출 조정
수리이며, 데이터 전수 정상화나 신규 레인의 H10/TP5/70% 자격 인증이 아니다.
